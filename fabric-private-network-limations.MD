# Microsoft Fabric Tenant-Level Network Security: Inbound and Outbound Limitations

**Scope:** Tenant-level settings only. Workspace-level configuration is addressed only where it is an unavoidable consequence of a tenant-level toggle, or where outbound protection is described (outbound protection has no tenant-level enforcement mechanism of its own; see Part C).

**Summary of mechanisms**

- **Inbound**: Tenant-level Private Link, Block Public Internet Access, Microsoft Entra Conditional Access, and Service Tags are configured and enforced at the tenant level.[[1]](https://learn.microsoft.com/en-us/fabric/security/security-inbound-overview)
- **Outbound**: Fabric has no tenant-level outbound restriction mechanism. "Workspace outbound access protection" (managed private endpoints and data connection rules) is workspace-scoped. The only tenant-level control is the toggle **Configure workspace-level outbound network rules**, which permits or forbids workspace administrators from enabling outbound protection but does not itself restrict traffic. Disabling it tenant-wide disables outbound protection in every workspace.[[4]](https://learn.microsoft.com/en-us/fabric/admin/service-admin-portal-advanced-networking)[[5]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-overview)

Because tenant-level enforcement exists only on the inbound side, the majority of hard limitations documented below are inbound limitations.

---

## Part A — Inbound (Tenant-Level): Dependencies

1. Public access can be restricted at the tenant level only when tenant-level Private Link is enabled; the two settings are linked.[[1]](https://learn.microsoft.com/en-us/fabric/security/security-inbound-overview)[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
2. Disabling the tenant setting **Configure workspace-level inbound network rules** reverts all workspaces to their prior inbound configuration.[[4]](https://learn.microsoft.com/en-us/fabric/admin/service-admin-portal-advanced-networking)
3. Access-matrix behavior for the public internet and tenant Private Link paths:[[1]](https://learn.microsoft.com/en-us/fabric/security/security-inbound-overview)
   - With Block Public Internet Access enabled and no Private Link connection, there is no access to the Fabric portal or the REST APIs from the public internet.
   - Over a tenant Private Link connection, portal access is unconditional — Microsoft's documentation lists this as "Yes" with no additional requirement.
   - REST API access over the same Private Link connection carries an additional requirement: the calling client (a workstation, server, CI/CD runner, or other process outside Fabric) must also retain its own path to the public internet, and must reach either the tenant-specific FQDN or the `api.fabric.microsoft.com` endpoint. The tenant-specific FQDN follows the pattern `<tenant-object-id-without-hyphens>-api.privatelink.analysis.windows.net`.[[7]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-use) This requirement does not apply to a Fabric notebook calling the REST API from inside Fabric, since that traffic is internal to the Microsoft backbone rather than an external inbound connection.
4. Conditional Access for Fabric is configured against related Azure services rather than a standalone "Microsoft Fabric" application, so a policy's effective scope can extend beyond Fabric. Microsoft's guidance targets five cloud applications: Power BI Service, Azure Data Explorer, Azure SQL Database, Azure Storage, and Azure Cosmos DB.[[6]](https://learn.microsoft.com/en-us/fabric/security/security-conditional-access#best-practices-for-fabric-conditional-access-policies) For example, a policy that targets Azure SQL Database to require MFA and a compliant device for Fabric's Warehouse and SQL analytics endpoints will apply that same requirement to any other, unrelated Azure SQL Database in the tenant, because the policy is scoped to the application as a whole. Microsoft's documentation also notes that an overly restrictive policy (for example, blocking all applications except Power BI) can break other Fabric features such as dataflows.[[6]](https://learn.microsoft.com/en-us/fabric/security/security-conditional-access#best-practices-for-fabric-conditional-access-policies)
5. Conditional Access requires Microsoft Entra ID P1 licensing.[[1]](https://learn.microsoft.com/en-us/fabric/security/security-inbound-overview)

## Part B — Inbound (Tenant-Level): Limitations

**Timing and rollout**
- Block Public Internet Access takes 10–20 minutes to take effect.[[4]](https://learn.microsoft.com/en-us/fabric/admin/service-admin-portal-advanced-networking)
- A newly created capacity does not support Private Link until DNS propagation completes, which can take up to 24 hours.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)

**Scale and infrastructure**
- Up to 450 capacities are supported per tenant with Private Link enabled.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- Tenant migration is blocked while Private Link is enabled.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- Fabric resources in multiple tenants cannot be reached from the same network location, since this is DNS-dependent; only the most recently configured tenant is reachable.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- Not supported with Trial capacity.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- Each private endpoint serves exactly one tenant; cross-tenant private endpoints are not supported. Cross-tenant scenarios, including cross-tenant OneLake sharing and shortcuts, are not supported over Private Link.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)

**Performance and cost**
- Non-data static resources (images, CSS, HTML) load from the private endpoint's region rather than the user's region, adding latency for geographically distant users.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- Private Link, and any additional ExpressRoute bandwidth required to support it, adds cost.[[2]](https://learn.microsoft.com/en-us/fabric/security/protect-inbound-traffic)
- The following endpoints must remain reachable from the client browser even with Private Link enforced:[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
  - Authentication: `login.microsoftonline.com`, `aadcdn.msauth.net`, `msauth.net`, `msftauth.net`, `graph.microsoft.com`, `login.live.com` (may vary by account type).
  - Data Engineering and Data Science experiences: `res.cdn.office.net`, `aznbcdn.notebooks.azure.net`, `pypi.org/*`, local static endpoints for conda packages, `cdn.jsdelivr.net/npm/monaco-editor*`.

**Tooling not supported tenant-wide with Private Link enabled**
- On-premises data gateways fail to register; virtual network (VNet) data gateways are supported as an alternative.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- VNet Data Gateway download diagnostics.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- Fabric Capacity Metrics app.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- OneLake Catalog Govern tab.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- Private link resource REST APIs do not support tags.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- Fabric IQ Plan (preview) items.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- Externally hosted images and custom theme files referenced within Power BI reports fail to load, since resolving them requires an outbound fetch that Block Public Internet Access blocks. This applies to report content, not portal branding.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)[[15]](https://community.fabric.microsoft.com/t5/Service/Power-BI-Private-Endpoint-quot-Azure-Private-Link-quot/m-p/2362209)

**Feature-specific limitations under tenant-level Azure Private Link / Block Public Internet Access**
- **OneLake**: Direct calls using OneLake regional endpoints do not work; cross-tenant shortcuts are not supported.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- **Warehouse**: Visual Query does not function with Block Public Internet Access enabled.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- **Spark, Lakehouse, and Notebook items**: The first Spark job or Lakehouse table operation provisions a managed VNet for the workspace, which disables prewarmed starter pools; a related Microsoft page on outbound protection for Data Engineering documents a resulting Spark session start time of 3 to 5 minutes, using the same underlying mechanism.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)[[13]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-data-engineering) Cross-region capacity migration is not supported once a managed VNet is allocated. Spark will not run for tenants whose home region does not support Fabric Data Engineering.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- **Pipeline**: Copying data into or out of a Data Warehouse is not currently possible.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- **Data agent**: Supported source types under Private Link are lakehouse, warehouse, and SQL data sources (the last referring to Fabric SQL Database, a standalone item distinct from Warehouse and from a Lakehouse SQL analytics endpoint). Kusto/Eventhouse sources, semantic models, and mirrored data sources are not supported as Data agent sources under Private Link. Cross-region Private Link access for SQL sources — that is, the Data agent and the Fabric SQL Database residing in different capacity regions — is also not supported.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- **Power BI**: A semantic model, Datamart, or Dataflow Gen1 that uses another Power BI semantic model or Dataflow as its own data source (for example, a composite model built on an existing semantic model) fails to connect when internet access is disabled, since this requires an item-to-item call blocked by the same setting. Additional documented breakage: Publish to Web fails; email subscriptions fail for all subscription types, including paginated reports; PDF/PowerPoint export fails; usage metrics return partial or no data; Copilot is unsupported; cross-tenant OneLake access is unsupported.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- **Eventstream**: Custom Endpoint as a source or destination, Eventhouse as a destination, and Activator as a destination are all unsupported.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- **Data Activator**: At the tenant level, ingestion from KQL/Eventhouse, Power BI, and Real-Time Hub Fabric Events (including OneLake events) continues to function over Private Link. Only Eventstream as a source is unsupported. Microsoft's documentation does not address pipeline-triggering scenarios specifically; this limitation is scoped to event ingestion sources.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- **Eventhouse**: Cannot ingest from OneLake, cannot be the target of a shortcut, cannot be connected to a pipeline, does not support queued ingestion, and does not support T-SQL queries.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- **Purview Information Protection**: Unsupported under Private Link. In Power BI Desktop on an isolated network, the Sensitivity button is disabled, label information does not appear, and `.pbix` decryption fails. A workaround exists via service tags for Exchange Online Protection and Azure Information Protection.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview) Separately, Purview Data Map scanning of Fabric is also not supported over tenant- or workspace-level Private Link, with a partial workaround of selecting the Virtual Network option on the connection screen and matching the Azure region between Fabric and Purview. Purview audit logging is unaffected by Private Link, since it is backend telemetry that does not route through the customer-controlled network path.
- **Mirrored database**: Private Link is supported for open mirroring, Azure Cosmos DB mirroring, Azure SQL Managed Instance mirroring, SAP mirroring, SharePoint List mirroring, and SQL Server 2025 mirroring. All other mirroring types pause while active and cannot be started while Block Public Internet Access is enabled.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview) On-premises SQL Server 2016–2022 (including SQL Server 2019 and 2022) mirrors via a dedicated, CDC-based "Mirroring for SQL Server" connector, which is distinct from both Open Mirroring and SQL Server 2025's mirroring mechanism (the Fabric mirroring change feed, which does not use CDC).[[8]](https://learn.microsoft.com/en-us/fabric/mirroring/sql-server) This CDC-based connector is not named on Microsoft's Private Link exception list and therefore falls under "other mirroring types," which is expected to pause under Block Public Internet Access.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview) It connects via an on-premises data gateway or a VNet data gateway; since on-premises gateways do not register under Private Link, a VNet data gateway is necessary to reach the source but is not sufficient to avoid this limitation, since the limitation stems from the mirroring type's absence from the exception list rather than from gateway connectivity.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- **API for GraphQL**: No support for Workspace Monitoring; service principals cannot be used to create a saved credential; artifact and data source pairs in different capacity regions fail authentication.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)

## Part C — Outbound: Dependencies and Limitations

Outbound protection has no tenant-level enforcement mechanism; it is configured entirely at the workspace level.

**Tenant-level dependency**
- The tenant setting **Configure workspace-level outbound network rules** must be enabled before any workspace administrator can configure outbound protection.[[4]](https://learn.microsoft.com/en-us/fabric/admin/service-admin-portal-advanced-networking)
- Disabling that tenant setting disables outbound access protection in every workspace tenant-wide.[[4]](https://learn.microsoft.com/en-us/fabric/admin/service-admin-portal-advanced-networking)
- If tenant-level Private Link (inbound) is enabled, the Fabric portal UI cannot be used to configure data connection rules (outbound); the Outbound Gateway Rules REST API must be used instead.[[5]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-overview)
- The Workspaces – List Networking Communication Policies admin API allows a tenant administrator to audit inbound and outbound policies across all workspaces from a single interface, though the underlying policies remain workspace-configured.[[5]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-overview)

**Mechanics of outbound protection (workspace-level)**
- When enabled on a workspace, all outbound connections are blocked by default. Exceptions are configured through one of two mechanisms depending on workload:[[5]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-overview)
  - **Managed private endpoints** — for Data Engineering and OneLake workloads: Lakehouses, Notebooks, Spark Job Definitions, Environments, and OneLake shortcuts. Also used to permit a protected workspace to reach another workspace in the same tenant, which requires the Private Link service to be enabled on the target workspace.
  - **Data connection rules** — for Data Factory (Dataflows Gen2 with CI/CD, Pipelines, Copy Jobs), Real-Time Intelligence (Activator, Eventstream, Eventhouse), Fabric IQ (Graph), mirrored databases, and Power BI semantic models.
- **Data Warehouse** (Warehouses, SQL analytics endpoints): Outbound protection blocks COPY INTO, OPENROWSET, and Bulk Insert against any external source (Azure Blob Storage, ADLS Gen2, or other storage accounts) — the commands Warehouse uses to load data. SQL analytics endpoint queries reaching a resource outside the current workspace are also blocked. No managed-private-endpoint exception is available for Warehouse, unlike Lakehouse. One exception: COPY INTO from OneLake itself continues to function, since it is an internal Fabric operation.[[12]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-data-warehouse)
- **Data Science** (Machine Learning Experiments, Machine Learning Models): No exception mechanism is available; Microsoft's support table lists this as "Not applicable." A page with the same level of specificity as the Data Warehouse documentation was not located for Data Science; this should be verified directly with Microsoft or through testing before being relied upon.[[5]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-overview)
- Allow-list granularity depends on the destination type: connector types that reference a Fabric item (Dataflows, Lakehouse, Warehouse, Fabric SQL Database, Notebook, Spark Job Definition) support workspace-level exceptions. Connector types that reference a destination outside Fabric (SQL Server, SharePoint, Analysis Services, OData, ADLS Gen2, Azure Blobs, Snowflake, PostgreSQL, Databricks, HTTP Server, REST Service, Amazon S3, Web v2, MySQL, Dataverse/CDS) support endpoint-level exceptions.[[5]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-overview)
- A workspace containing unsupported artifact types cannot enable outbound protection until those artifacts are removed. Once enabled, unsupported artifacts cannot be added without first disabling protection.[[5]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-overview)

**Additional limitations**
- Available only in regions that support Fabric Data Engineering workloads.[[5]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-overview)
- Supported only on Fabric SKU capacities; other capacity types and F SKU trials are not supported.[[5]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-overview)[[14]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-set-up)
- Requires re-registering the `Microsoft.Network` resource provider on the Azure subscription (Azure portal: Subscriptions > Settings > Resource providers > Microsoft.Network > Re-register).[[14]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-set-up) Microsoft's documentation lists this as a prerequisite step without explaining the underlying reason. The most plausible explanation is that this refreshes the subscription's registration with the provider so that it recognizes the networking resource types (for example, managed private endpoints) that outbound access protection provisions; this explanation is inferred and not confirmed by Microsoft documentation.
- Notebooks in a protected workspace cannot query Warehouse file paths via the `dbo` schema; T-SQL must be used instead.[[5]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-overview)
- Not compatible with OneLake Diagnostics unless the diagnostics Lakehouse resides in the same workspace.[[5]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-overview)
- Not compatible with Fabric external data sharing; cross-tenant allow lists are not supported.[[5]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-overview)
- Power BI items other than semantic models (reports, dataflows, and so on) do not support outbound protection: they cannot be created in a protected workspace, and if they already exist, protection cannot be enabled on that workspace.[[5]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-overview)
- `pip install` from PyPI within notebooks is blocked entirely (not merely slower) when outbound access protection is enabled on the workspace. This is documented specifically for outbound protection; it is not confirmed whether inbound Private Link alone (without outbound protection) produces the same restriction, since the managed VNet that inbound Private Link provisions may still permit general outbound internet access absent the separate outbound protection toggle. Workarounds are to upload `.whl` files manually or host a private PyPI mirror on Azure Storage, reached via a managed private endpoint.[[13]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-data-engineering)
- In cross-workspace access scenarios with outbound access protection enabled on the consuming workspace, Spark DataFrame reads (for example, `spark.read.table()`) continue to function against a schema-enabled Lakehouse in another workspace, but Spark SQL statements (for example, `SELECT * FROM table`) may fail. A cross-workspace managed private endpoint is the documented remedy.[[13]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-data-engineering)

## Part D — Applied to the Proposed Architecture

The proposed architecture: mirror two databases from an on-premises SQL Server 2022 instance; an Azure Function writes files directly into a Lakehouse in OneLake; Materialized Lake Views build the silver and gold layers, supplemented by notebooks; several semantic models in both Import and Direct Lake modes; several Power BI interactive and paginated reports. The analysis below assumes tenant-level Private Link is enabled and Block Public Internet Access is on.

### Breaks or requires a workaround

- **SQL Server 2022 mirroring (both databases)**: SQL Server 2016–2022 CDC-based mirroring is not on Microsoft's Private Link exception list. Active mirrors pause, and new ones cannot be started, while Block Public Internet Access is enabled. An existing VNet data gateway resolves connectivity to the on-premises source but does not resolve this limitation. Two workarounds: migrate these two databases to Open Mirroring, which requires a custom publisher writing to the OneLake landing zone via Private Link, or defer until migration to SQL Server 2025, whose native mirroring is on the supported list.[[8]](https://learn.microsoft.com/en-us/fabric/mirroring/sql-server)[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- **Publish to Web, PDF/PowerPoint export, email subscriptions, Copilot, and usage metrics**, for both interactive and paginated Power BI reports: these capabilities break under Block Public Internet Access regardless of report type. Email subscription failure is confirmed for both report types. PDF/PowerPoint export failure is documented for interactive reports; whether this extends to paginated reports specifically (which render through a different, RDL-based engine) is not confirmed in Microsoft's documentation and should be verified through direct testing. No workaround exists short of disabling Block Public Internet Access for the operations that require these features.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- **`pip install` from PyPI within notebooks**: Confirmed blocked under outbound access protection specifically, not under inbound Private Link/Block Public Internet Access alone, which is the current scope of this analysis. Whether inbound protection alone produces the same restriction is not confirmed. If outbound protection is added to this workspace in the future — a reasonable control given it is the feature that prevents data exfiltration — `pip install` will stop functioning entirely. This should factor into the decision of whether notebooks in this environment install packages at runtime.[[13]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-data-engineering)
- **Spark SQL against a cross-workspace, schema-enabled Lakehouse**: Also conditional on outbound protection, and directly relevant to the proposed use of Materialized Lake Views, which are defined using Spark SQL syntax (`CREATE MATERIALIZED LAKE VIEW ... AS SELECT ...`). If a silver- or gold-layer Materialized Lake View queries a Lakehouse in a different workspace than the view itself, and outbound protection is later enabled on the consuming workspace, the view's defining query is the type of statement this limitation affects (DataFrame reads continue to work; Spark SQL statements may fail). Keeping mirrored sources, Materialized Lake Views, and their consuming Lakehouse within the same workspace avoids this; a cross-workspace managed private endpoint is the documented alternative.[[13]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-data-engineering)

### Works, but requires specific configuration

- **Azure Function writing to OneLake**: Per Microsoft's Fabric platform architecture documentation, attempts to use Fabric from outside the VNet, or without the private endpoint, are rejected when Block Public Internet Access is enabled. OneLake is ADLS Gen2 API–compatible, so a Function can read and write it directly, provided the Function itself is VNet-integrated (Premium or Elastic Premium plan, or otherwise placed inside the VNet) so its calls route through the private endpoint. A default Consumption-plan Function calling the public OneLake endpoint would be rejected. This requires deliberate networking configuration rather than a code change.[[11]](https://learn.microsoft.com/en-us/fabric/fundamentals/external-integration)

### Should function as designed

- **Materialized Lake Views**: Explicitly supported in Private Link–enabled Lakehouses. Refreshing them via the Fabric portal or REST APIs in a Private Link workspace is documented as functional, currently flagged as preview functionality. See the cross-workspace caveat above if outbound protection is added later.
- **Notebooks**: Function under both inbound Private Link and outbound access protection, via the same underlying managed VNet mechanism. Microsoft's Data Engineering outbound-protection documentation specifies a resulting Spark session start time of 3 to 5 minutes once starter pools are disabled, in place of the near-instant start from a prewarmed pool. See the `pip install` and cross-workspace Spark SQL items above for the more significant considerations.[[13]](https://learn.microsoft.com/en-us/fabric/security/workspace-outbound-access-protection-data-engineering)
- **Import-mode semantic models** built on gold-layer Lakehouse or Warehouse tables: This is internal Fabric-to-Fabric traffic over the Microsoft backbone rather than a public-internet inbound path, so it is not blocked by Block Public Internet Access. The documented exception is a semantic model built to import from another semantic model or Dataflow (a chained or composite reference) rather than directly from the Lakehouse; that specific pattern fails under Block Public Internet Access (see Part B). Building directly from Lakehouse or Warehouse tables avoids this.[[3]](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- **Direct Lake semantic models**: Also internal Fabric-to-OneLake traffic via the ADLS Gen2 connector, and therefore not blocked by tenant-level Block Public Internet Access alone. Microsoft's documentation separately notes that Direct Lake is not yet supported against data sources in a workspace with inbound access explicitly restricted at the workspace level (workspace-level "Restrict public access," distinct from the tenant setting). This does not apply to the architecture as described, but is relevant if workspace-level restriction is added in the future.[[16]](https://learn.microsoft.com/en-us/fabric/security/security-workspace-level-private-links-support)
- **Interactive Power BI reports**: Viewing and interacting within the Fabric portal continues to function, since Private Link restores portal access. See the breakage list above for the specific capabilities that do not function.
- **Paginated reports**: Viewing and rendering within the portal is expected to function the same way as interactive reports, via the same portal access path. See the breakage list above for the specific capabilities that do not function.

## Related but Distinct: Entra Tenant Restrictions v2

Included for completeness in case this broader identity-layer control, rather than Fabric-specific network security, was the intended scope. This is genuinely tenant-level and not Fabric-specific.

- Incompatible with macOS Platform SSO combined with corporate-proxy client signaling, if the proxy's certificate chain is outside Apple's trusted roots.[[17]](https://learn.microsoft.com/en-us/entra/external-id/tenant-restrictions-v2)
- Proxy-based signaling injects headers only at the authentication plane, not the data plane.[[17]](https://learn.microsoft.com/en-us/entra/external-id/tenant-restrictions-v2)
- ExpressRoute cannot perform header injection itself, since it does not terminate TLS or inspect HTTP; a proxy or firewall upstream of ExpressRoute is required.[[17]](https://learn.microsoft.com/en-us/entra/external-id/tenant-restrictions-v2)
- The Azure DevOps connector in Power Platform does not enforce tenant isolation policy; this is a documented, known gap.[[18]](https://learn.microsoft.com/en-us/power-platform/admin/cross-tenant-restrictions)
